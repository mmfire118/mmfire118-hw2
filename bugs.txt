1) Text parsing supports only 0-10; broader English numbers fail
   - Symptoms: "eleven", "twenty one", "one hundred twenty three", etc. return error
   - Hyphenated/extra-spaced forms (e.g., "twenty-one", " Twenty-One ") also fail
   - README mismatch: example "forty two" fails
   - Likely cause: text_to_number uses a hardcoded dictionary for 1..10 only
   - Tests: tests/test_text_issues.py::test_text_numbers_beyond_ten_should_work
            tests/test_text_issues.py::test_readme_example_forty_two_should_work
            tests/test_text_issues.py::test_hyphenated_and_whitespace_text_should_work

2) Base64 endianness mismatch (app uses big-endian; requirement expects little-endian by default)
   - Symptoms: decimal->base64 base64 output differs for values like 256, 4096
   - Tests: tests/test_api_conversions.py::test_base64_roundtrip_little_endian

3) Decimal 0 encodes to empty base64 string
   - Symptoms: "0" (decimal) -> base64 yields empty string ""
   - Likely cause: number_to_base64 computes 0-byte length; base64 of empty bytes is ""
   - Tests: tests/test_base64_edge_cases.py::test_zero_base64_encoding_explicit_zero_length

4) Invalid base64 inputs can decode to 0 instead of error
   - Symptoms: "**" as base64 -> decimal returns 0, not an error
   - Likely cause: base64.b64decode called without strict validation; empty bytes -> int 0
   - Tests: tests/test_api_conversions.py::test_invalid_inputs_return_error[**-base64]

5) Negative numbers produce mangled binary/octal/hex outputs
   - Symptoms: negative inputs drop sign/prefix after slicing (e.g., "-1" -> binary "b1")
   - Likely cause: uses bin/oct/hex then slices [2:], which corrupts negatives like "-0b101" -> "b101"
   - Tests: tests/test_negative_numbers.py::test_negative_to_non_decimal_outputs[...]

6) Negative numbers to base64 likely fail
   - Symptoms: negative decimal -> base64 raises error (not handled)
   - Likely cause: int.to_bytes for negative numbers requires signed=True, but code uses default
   - Tests: tests/test_base64_edge_cases.py::test_negative_decimal_to_base64_should_work

7) All errors return HTTP 200 with an error field instead of 4xx
   - Symptoms: Missing fields/invalid inputs respond 200 with {result: null, error: str}
   - Concern: HTTP semantics; clients cannot distinguish success vs error by status
   - Tests: tests/test_api_errors.py (expects current 200 behavior but flagged as issue here)

8) Error messages may leak internal details
   - Symptoms: raw exception strings are returned to clients
   - Risk: information disclosure; inconsistent client UX
   - Tests: tests/test_api_errors.py::test_error_message_should_be_generic

   - Tests: tests/test_code_quality_unused_imports.py::test_text2digits_import_is_used
